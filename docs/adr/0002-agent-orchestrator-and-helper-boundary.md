# 2. Agent Orchestrator 编排器与确定性 Helper Tools 职责边界及动态补查原则

日期: 2026-08-15

## 状态

已通过 (Accepted)

## 上下文与问题陈述

Career Radar 系统在每日运行时，既涉及大量确定性的数据抓取、附件文档读取、本地状态读写等机械任务，又需要对非结构化、充满隐性条款与来源冲突的招聘信息进行高精度的语义推理与业务决策。若未能清晰界定系统职责边界，极易导致架构出现两类失衡：
1. **策略下沉与机械误杀**：若将业务初筛、关键词过滤或业务状态转换规则编码进底层辅助程序，会导致系统僵化并造成边缘有效岗位的不可逆误杀；
2. **职责混乱与失控调用**：若底层辅助程序脱离确定性约束或越权进行业务策略决策，或 Agent 在缺乏预算约束下无休止地发起外部重试与调用，会导致执行不可控。

## 决策

我们决定确立 **Agent 作为唯一业务编排中枢与 Helper Tools 保持确定性/无业务策略偏见** 的架构职责边界及动态补查原则：

1. **Scheduler 唤醒契约与业务解耦**：
   - 定时调度器（Scheduler）仅负责周期性唤醒 Agent，不拥有或干预 Career Radar 的具体业务流程；
   - Scheduler 可接收粗粒度的 machine-readable Run Outcome 用于外部健康监控，但系统不在此锁定具体的 CLI/API 形式、环境变量、特定执行模式或状态码 Schema。

2. **Agent 拥有编排权威与业务决策权**：
   - Agent 是系统唯一的 Workflow Orchestrator 与语义/业务决策权威（Semantic & Business Decision Authority）；
   - 业务状态的定义、解释以及所有的业务状态转换决定权完全由 Agent 掌握。

3. **Helper Tools 的确定性、无业务偏见与状态持久化契约**：
   - Helper 必须保持确定性（Deterministic）且无业务策略偏见（Policy-Free），严禁在 Helper 内部进行业务过滤或资格初筛；
   - Helper 并非无状态，明确允许承载状态持久化能力（State Persistence），执行确定性的已见记录读写与状态存储；
   - Helper 允许承载复合机械操作（Composite Mechanical Operations），不强求拆解为单一细粒度的原子工具；
   - Helper 保留并返回可追溯的机械来源与错误信息；所有返回数据的“证据业务含义”交由 Agent 自行解释与判定；
   - Helper 仅执行确定性的查询与写入操作，并可处理有限的确定性技术恢复（如基础网络层重试）；但“是否更换来源/工具、是否继续调查以及是否消耗调查预算”完全由 Agent 裁决。

4. **动态证据补查与调查预算约束**：
   - 当遇到 Evidence Gap（信息缺失、证据不足、多源冲突或抓取异常）时，Agent 可根据上下文动态选择已批准能力（如解析附件、回溯第一方官网、外部搜索等）进行深度补查；
   - 补查行为受调查预算（Investigation Budget）与停止条件（Stop Conditions）约束，防止无限发散；具体预算数值、调用上限与特定服务 Provider 留待后续具体设计，不在此静态锁定。

## 后果与权衡

### 积极影响
- **业务决策权集中**：确保所有业务逻辑、语义判断与状态转换均由 Agent 统一把控，杜绝底层机械过滤带来的误杀；
- **底座清晰稳定**：Helper 工具保持纯粹的确定性与可追溯性，允许灵活组合复合机械操作并安全管理状态持久化；
- **弹性与可控性平衡**：Agent 具备动态补查的自主性，同时受调查预算硬性约束。

### 潜在代价
- 系统的执行时间与资源消耗取决于每次运行发现的待审机会量及 Agent 动态决策的补查深度。
